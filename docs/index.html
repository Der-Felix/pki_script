OpenSSL 3.x Native • RFC 5280 Strict

Zero-compromise PKI for Homelab & Enterprise

A modular, file-based Public Key Infrastructure engine. Designed for air-gapped Root CAs, delegated intermediate authorities, Apple/RFC-compliant leaf certificates, 802.1X EAP-TLS, and automated headless deployment.

2-Tier CA Hierarchy Automated Chain Bundles PKCS#12 (.p12) Protected Zero External Dependencies

Overview & Design Philosophy

Most homelab PKI setups either rely on single self-signed certificates (which break constantly and must be manually trusted on every device upon renewal) or heavyweight GUI platforms (Vault, Smallstep) that introduce daemon dependencies, Postgres databases, and resource overhead.

This suite is built in clean POSIX/Bash across 17 specialized libraries under lib/. It utilizes standard Unix directory layouts, OpenSSL 3.x modern cryptography, and delivers complete bundles: fullchain.pem, combined.pem, password-protected cert.p12 archives, and auto-generated copy-paste deployment instructions (GUIDE.txt).

Why File-Based PKI?

All state is stored cleanly on disk. You can audit certificates with plain OpenSSL commands, back up the directory with Git, rsync, restic, or Borg, and run on offline Raspberry Pis, air-gapped flash drives, or cloud instances with zero background services consuming memory.

Two-Tier CA Architecture & Security

In a production security model, the Root CA must never issue leaf certificates directly. If a Root CA private key is ever exposed, every certificate trust anchor across your laptops, phones, switches, and servers must be manually wiped and replaced.

Key Architectural Constraints

1. Path Length Constraint (pathlen:0): The Intermediate CAs are issued with X.509 extension basicConstraints = critical, CA:TRUE, pathlen:0. This cryptographic rule ensures an intermediate CA can issue end-entity leaf certificates, but cannot issue additional sub-CAs under any circumstances.

2. Role Segregation via Extended Key Usage (EKU): Web servers receive strictly serverAuth. Client certificates receive strictly clientAuth. This prevents leaf certificates from being abused across security boundaries.

3. Cold-Storage Root Safety: Because the Root CA signs only the Intermediates (every 10 years), the Root CA private key can be kept completely offline (e.g. on an encrypted flash drive or cold disk). Daily certificate operations only touch the Intermediate CAs.

30-Second Quickstart

Get a full production-grade Root CA, two issuing intermediate authorities, and your first verified certificate up and running in under a minute:

1. Clone & Check Dependencies

Terminal 
git clone https://github.com/Der-Felix/pki_script.git
cd pki_script
chmod +x pki.sh build.sh pki completions/pki.bash
./pki.sh doctor

2. Initialize Root CA and Intermediate Authorities

The init command creates the offline Root CA and both issuing CAs in one single operation:

Terminal 
./pki.sh init --org "Homelab" --intermediate server-ca --intermediate client-ca

3. Issue a TLS Server Certificate with 1-Click DNS Discovery

The quick command automatically performs forward and reverse DNS lookups, resolving all host aliases and local IP addresses into SAN extensions:

Terminal 
./pki.sh quick web01.homelab.lan

4. Verify Cryptographic Integrity

Terminal 
./pki.sh verify web01.homelab.lan --host web01.homelab.lan

Strict SAN Enforcement (Why CommonName is Dead)

Many legacy scripts still put the hostname in the certificate Subject CommonName (CN) and omit Subject Alternative Names. In modern TLS, this guarantees connection failure.

Mandatory Standards

Since Google Chrome 58, Apple iOS 13, macOS Catalina, and Go 1.15, the commonName field is completely ignored for hostname validation. A certificate must have an explicit subjectAltName extension.

Important: DNS SAN ≠ IP SAN! If you connect to https://192.168.1.10, having a DNS SAN is not enough; the certificate must contain an explicit IP:192.168.1.10 entry.

Why RFC Standards? The X.509 & TLS Blueprint

In cryptography, universal consensus on data formats and validation algorithms is non-negotiable. Without Requests for Comments (RFCs) curated by the Internet Engineering Task Force (IETF), secure cross-vendor networking would be impossible. A certificate generated on a Linux host must be validated identically by Windows Schannel, Apple SecureTransport, Google Chrome, Firefox, and curl without ambiguity.

Why RFC Standards Matter in Your Homelab

Many ad-hoc scripts create certificates that look functional but fail abruptly against modern operating systems: missing SANs trigger security warnings, improper Key Usage bits prevent TLS handshakes, and excessive validity lengths cause hard rejections. This suite adheres strictly to production RFC standards:

RFC 5280
RFC 5280: The X.509 & CRL Core Specification

Defines the canonical format of Version 3 certificates, mandatory fields, and extensions including basicConstraints (CA:TRUE vs. FALSE, pathlen:0), keyUsage, and Certificate Revocation Lists (CRLs).

RFC 2818
RFC 2818: HTTP Over TLS (HTTPS)

Formally deprecated commonName for web identity verification and mandated Subject Alternative Names (SAN, DNS: and IP:) for all HTTPS hosts.

RFC 8446 • 5246
RFC 8446 / 5246: TLS 1.3 & 1.2 Handshakes

Governs the cryptographic handshake. Dictates that servers send full intermediate chains (fullchain.pem) in ServerHello, but NEVER transmit the Root CA certificate.

RFC 5216
RFC 5216: EAP-TLS Network Authentication

The bedrock standard for 802.1X (RADIUS / WPA2-Enterprise). Enforces strict role separation: RADIUS servers require EKU serverAuth; client endpoints require EKU clientAuth.

RFC 8555
RFC 8555: ACME Automation

The automated certificate management protocol powering Let's Encrypt and Step-CA for zero-touch issuance and HTTP-01 / DNS-01 challenge verification.

CA/B Forum
CA/Browser Forum Baseline Requirements

The mandatory baseline enforced by all major platform vendors (Apple, Google, Microsoft): maximum 398-day validity for leaf certificates and SHA-256 signatures.

802.1X EAP-TLS Network Authentication (Wi-Fi / LAN)

EAP-TLS is the highest security standard for wireless (WPA2/WPA3-Enterprise) and dynamic switch port admission. Passwords are never used. Instead, authentication relies on mutual cryptographic verification between the user's device and the RADIUS server.

1. Issue the FreeRADIUS Server Certificate

Terminal 
./pki.sh issue server --cn radius.homelab.lan --dns radius.homelab.lan --ip 192.168.1.15

2. Issue User & Device Client Certificates

Terminal 
./pki.sh issue client --cn "laptop-felix" --email felix@homelab.lan --p12

3. Client Deployment

  • Windows / macOS / iPhone / Android: Import the generated pki/issued/laptop-felix/cert.p12 into the User Certificate store. Install pki/publish/root.crt into Trusted Root Certification Authorities.
  • Linux (/etc/wpa_supplicant/wpa_supplicant.conf):
    wpa_supplicant.conf
    network={
    ssid="Homelab-Enterprise"
    key_mgmt=WPA-EAP
    eap=TLS
    identity="laptop-felix"
    ca_cert="/etc/ssl/pki/root.crt"
    client_cert="/etc/ssl/pki/laptop-felix.pem"
    private_key="/etc/ssl/pki/laptop-felix.key"
}

Web Ingress & Reverse Proxy Integration

Every issued certificate folder includes auto-generated configuration blocks in GUIDE.txt. Switch tabs below to see tested configuration snippets for all major web servers:

server {
    listen 443 ssl http2;
    listen [::]:443 ssl http2;
    server_name web01.homelab.lan;

    ssl_certificate     /etc/ssl/web01/fullchain.pem;
    ssl_certificate_key /etc/ssl/web01/key.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;

    location / {
        proxy_pass http://127.0.0.1:8080;
    }
}
# dynamic.yml (Traefik File Provider)
tls:
  certificates:
    - certFile: /certs/fullchain.pem
      keyFile:  /certs/key.pem
  stores:
    default:
      defaultCertificate:
        certFile: /certs/fullchain.pem
        keyFile:  /certs/key.pem
web01.homelab.lan {
    tls /etc/ssl/web01/fullchain.pem /etc/ssl/web01/key.pem
    reverse_proxy 127.0.0.1:8080
}
<VirtualHost *:443>
    ServerName web01.homelab.lan
    SSLEngine on
    SSLCertificateFile    /etc/ssl/web01/fullchain.pem
    SSLCertificateKeyFile /etc/ssl/web01/key.pem
    SSLProtocol -all +TLSv1.2 +TLSv1.3
</VirtualHost>
# HAProxy requires combined.pem (private key + cert chain bundled together)
frontend https-in
    bind :443 ssl crt /etc/haproxy/certs/combined.pem alpn h2,http/1.1
    default_backend homelab_apps

scp fullchain.pem root@pve01:/etc/pve/local/pveproxy-ssl.pem

# Restart pveproxy to apply instantly

TrueNAS SCALE / CORE

In TrueNAS WebGUI: Go to Credentials → Certificates → Click Add → Select Import Certificate. Paste the contents of key.pem into Private Key and fullchain.pem into Certificate. Then under System → General, select the imported certificate as the WebGUI SSL cert.

Importing Root CA into Client Trust Stores (Once per device)

Once you install the public Root CA (pki/publish/root.crt) on your devices, every certificate issued by your Intermediate CAs will be automatically trusted across Chrome, Safari, Edge, curl, and native apps with zero security warnings.

Platform / Client Installation Instructions
Windows (PowerShell Admin) Import-Certificate -FilePath .\pki\publish\root.crt -CertStoreLocation Cert:\LocalMachine\Root
macOS (System Keychain) sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain pki/publish/root.crt
Debian / Ubuntu / Proxmox sudo cp pki/publish/root.crt /usr/local/share/ca-certificates/homelab-root.crt && sudo update-ca-certificates
RHEL / Rocky / Fedora sudo cp pki/publish/root.crt /etc/pki/ca-trust/source/anchors/homelab-root.crt && sudo update-ca-trust
Apple iOS (iPhone / iPad) AirDrop or download root.crt → Settings → Profile Downloaded → Install. Then: Settings → General → About → Certificate Trust Settings → Enable Full Trust.
Android Settings → Security → Encryption & credentials → Install a certificate → CA certificate → Select root.crt.
Firefox Browser Open about:config → Set security.enterprise_roots.enabled to true. Firefox will inherit the OS trust store.

Because the PKI is purely file-based, backup and recovery is as simple as creating an encrypted archive:

Headless Automation & Cron Renewal

Automate certificate renewal in cron jobs, Ansible playbooks, or SaltStack states with environment variables:

Battle-Tested Tips & Tricks for Homelab & Enterprise

Practical engineering insights, operational shortcuts, and common pitfalls learned from deploying X.509 PKIs:

TIP #1 The "10-Year CA, 397-Day Leaf" Rule

Since September 2020, Apple Safari, Google Chrome, and iOS reject leaf certificates valid for longer than 398 days. Your Root and Intermediate CAs can be valid for 10–20 years, but leaf certificates must always be capped at 397 days (--days 397).

TIP #2 The Common SAN Trap: DNS Name vs. IP Address

Connecting to https://192.168.1.10 will trigger a certificate error if the certificate only contains DNS:web.lan! Clients strictly match the address bar input. Always pass both DNS and IP addresses: --dns web01.lan --ip 192.168.1.10.

TIP #3 Instant Certificate Inspection in Terminal

Avoid typing verbose OpenSSL commands. Use pki.sh inspect cert.crt or a quick shell alias: openssl x509 -in cert.crt -noout -text | grep -E 'Subject:|Issuer:|Not After|DNS:|IP:'.

TIP #4 Zero-Downtime Reload for Nginx, Caddy & Traefik

Never use restart when updating certificates on live ingress! Use systemctl reload nginx or caddy reload: existing connections stay open, while new handshakes immediately serve the fresh certificate.

TIP #5 Java Keystore Trust (Unifi Controller, Elasticsearch, Minecraft)

Java applications do not query the operating system certificate store; they rely on their own cacerts keystore. Import your Root CA with: keytool -import -trustcacerts -keystore $JAVA_HOME/lib/security/cacerts -storepass changeit -alias homelab-root -file root.crt.

TIP #6 PKCS#12 (.p12) for 1-Click Install on Windows & Apple

Passing --p12 packages the leaf certificate, private key, and intermediate chain into an encrypted cert.p12 bundle. Double-click the file on Windows or Apple devices and enter the passphrase for instant import into the user store.

TIP #7 Git Security & Cold-Storage for the Root CA

Version control your pki/ repository, but keep all *.key files excluded in .gitignore. Back up pki/root-ca/private/root.key to two encrypted USB drives, then remove it from the live server (Cold Storage).
